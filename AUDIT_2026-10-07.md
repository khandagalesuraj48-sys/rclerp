## B. Findings that were fixed (each: where → what was wrong → evidence on the live code → the fix → the test)

### High

**H1 – A saved bill could carry HTML that ran on the screen of whoever opened it (stored XSS).**
`app/App.html` `mbDot`, `billHtml` (dates, unit, nights of the bill's stored data went into the papers unescaped);
`app/Code.gs` `submitBills_` stores the page's data blob as it comes.
Evidence (live code): a bill whose stored data had `<img onerror=…>` in its dates ran that script **13 times** in the print
window and reached the app page that opened it (where the sign-in token lives). Needs a user who may save bills; hits
anybody who opens the bill, also the Admin.
Fix: every value of a bill's data is escaped where it enters a paper (`mbDot`, `showDate`, unit, nights); the server
refuses a bill whose data holds text that looks like HTML (`billNoHtml_` – "a < b", "5<10" stay allowed); six more
typed values wrapped in `esc()`.
Test: `test/browser/viewbill.js` step 2b – before: ran 13, after: ran 0, shown as text 13 times; unit test 39.

**H2 – After a network hiccup an entry could be saved twice.**
`server/runtime.js` `run` / `runPlain`, `app/Code.gs` `withLock_` / `apiRun_`. An entry is written, then three housekeeping
steps follow (give the lock back, write the Activity Log line, write data versions / sign-in time). If one of them failed
the request answered "could not reach the database"; the page – by design – sent the same entry again; the server had
freed its number, so it was saved a SECOND time (a second Diesel Issue number, stock counted twice).
Evidence (live code, fault injected after the write): housekeeping write fails → the copy sent again is saved again,
**2 rows**; lock cannot be given back → error for a saved entry and the lock left for 75 s; Activity Log line fails →
"Could not save" for an entry that IS saved.
Fix: the moment the entry is in the database is marked (`SAVED_`, `__saved`); failures after it no longer turn the answer
into an error (the fault is noted for the Admin), the lock is given back at the end of the request, and an entry that is
saved is never run again by itself.
Test: `test/harden.js aftersave` (a)–(d): before 4 fail, after 5 pass; (d) proves a save that really failed still fails.
*Left (D7):* a write that times out after 30 s without any answer is still treated as "not saved".

**H3 – One hiccup switched the exact counters off for the life of the server.**
`server/runtime.js` (`/404|web_count/` matched EVERY error of that function, not only "not installed"). After one failed
call: the sign-in limit and "the same entry sent twice is saved once" silently used the weaker read-then-write way.
Evidence (live code): after one injected hiccup the same entry sent twice was **saved twice**.
Fix: only the database's "function not found" (404) switches them off. Test: `harden.js counters`.

**H4 – Without its "all or nothing" function a save was written table by table – silently, and for good.**
`app/SupabaseData.gs` `flush`. If `web_write` (step-3 SQL) answered "not found", the save went one call per table (one
may fail, the others stay) and the server stayed in that mode until restart. Evidence (live code): saved "the old way".
Fix: the save is REFUSED, names `sql/supabase_step3_safety.sql`, nothing is written; the old way only if the server's
owner sets `RCL_OLD_WRITES=on`. (The live database has the function: the app's "Database ✓" check of 07-10-2026 includes
it.) Test: `harden.js failclosed`.

**H5 – A one-time password gave the whole app, and lay in the table as typed.**
`app/Code.gs` `api`, `saveUserAdmin_`, `checkPw_`. Only the PAGE asked for the new password: reloading the page instead
left the person signed in with full access for as long as they liked. The password was stored in plain text until changed.
Evidence (live code): `getInit` and a save both worked on the one-time password.
Fix: the server opens nothing until an own password is set; a one-time password is stored as a hash with a "must change"
mark (`tmp$sha256$…`). A plain password written by hand into the table (first Admin of a new site) still works and must
be changed. Test: `harden.js auth` (3 lines), `audit.js auth`.

**H6 – Program code was fetched from public file servers into the signed-in page.**
`app/App.html` (SheetJS from cdnjs at every start – also on the sign-in screen; ExcelJS from jsDelivr / cdnjs), no
integrity check. Whoever controls such a server or the road to it could run code next to the sign-in token.
Fix: both tools are files of the app (`app/vendor/`, the unchanged package files, sha256 in the README there), served from
the app's own address; the public address is only the second try (old Apps Script hosting). Excel now also works where
those servers are blocked. Test: viewbill step 0 and hardenpage (every script from the app's address, formatted Excel made).

### Medium

**M1 – The link of the backup Sheet went to every signed-in user.** `apiRun_` put `sbBackupInfo_()` (with `url`) into every
heartbeat; the page showed "Open the backup Google Sheet". The Sheet holds every table (vendors' bank / PAN / Aadhaar,
Activity Log). Fix: link and technical error text only for the Admin (`backupInfoFor_`). The old Apps Script code that set
the Sheet to "anyone with the link" (`sbShareViewOnly_`, not reachable on Vercel) now sets it to private. **See D1.**
Test: `backup.js privacy`, `failure`.

**M2 – A value for a column the database does not have was dropped, and the save said "saved".** `SupabaseData.gs`
`toRecord_`. Fix: an empty value is left out as before; a VALUE is never dropped – the save is refused and names the
column. Test: `harden.js column` (column removed in the rig, then put back).

**M3 – Backup: all or nothing, and silent when cut off.** `server/backup.vm.js`. A backup longer than the 58 s a request
may run was cut off with nothing noted; every later one started from the beginning and was cut off again, while the app
showed the last good time in green. Also: 3 tries of up to 50 s each against Google could outlast the request; after a
failure every open page started the failing backup again at once; the nightly job logged "200 OK" for a failed backup.
Fix: tables are written in groups, smallest first, progress noted after every group; a run stops by itself after ~36 s and
the next asking goes on with what is left; a run that is cut off leaves a mark – after two in a row the app shows the
backup as failed; Google calls respect the remaining time; 4-minute wait also after a failure; the nightly job answers 500
when it fails. Test: `backup.js pieces`, `cutoff` (server killed twice in the middle), `failure`, `cron`.
*Left (D8):* one table that alone needs more than ~50 s (far from today's sizes) – now at least visible as a failure.

**M4 – Text was changed on its way into the backup Sheet.** Values were sent for the Sheet to interpret: an account number
`000123456789012345` became a number (leading zeros gone, long numbers rounded), a challan "12/5" a date.
Fix: every text is marked as text; dates stay dates. Test: `backup.js text`.

**M5 – The assistant's limits could be passed.** `getAiReply_` read the count, asked the AI service, wrote count + 1 at the
end: N questions at the same moment counted as one. Fix: counted with the exact counter. Test: `harden.js ai` (21 = 21).

**M6 – A chat of more than 40 turns stopped answering** ("Type a question for the assistant" until "New chat").
Fix: the cut conversation starts at the first typed question. Test: `harden.js ai`.

**M7 – The server's waiting line had no end.** `server/pool.js`: unlimited queue, its clock started only at dispatch.
Fix: at most 120 wait (`RCL_QUEUE`); the next is told "busy" (503 + Retry-After) at once – the page re-sends a save by
itself; the 58 s count from arrival. Test: `harden.js queue` (60 at once on 1 thread: 12 answered, 48 told busy in < 0.1 s).

**M8 – A locked e-mail was locked again by every further try** (also by anybody else, for ever). `login`.
Fix: a try while locked is refused without being counted. Test: `harden.js auth`.

**M9 – Two Activity Log lines written at the same moment shared a number and one replaced the other.** `writeLog_`.
Fix: the key carries 4 random characters. Test: 12 sign-ins at once → 12 lines.

**M10 – Deleting a bill passed over ANY failure of freeing its debit notes** and answered "ok". `deleteBill_`.
Fix: only "there is no debit-notes table" is passed over; anything else fails the whole delete.

**M11 – Browser: the redraw limiter never ran** (its `clearTimeout` had slipped into a comment): five changes = five
redraws of the page on screen. Fix: one. Test: hardenpage 4 (before 5, after 1).

### Low

- **L1 Freeze recorder** wrote ~12 KB to the browser's storage every second (86,000 times a day per open page) and showed
  "the page stopped without closing properly" for a second tab or a phone that ended a background app. Now: written only
  when there is something new; background = closed properly; another open tab is asked first. (before 10 writes / 10 s,
  after 0; false alarm gone; a page that really died is still reported.)
- **L2 Sign-out** left the person's settings copy (mobile number, photo) and the Admin's database check in the browser. Removed.
- **L3 Offline copy:** any address opened in a tab (an icon) replaced the kept page. Fixed.
- **L4 HTTP status:** every failure answered 200. Now 401 / 403 / 404 / 429 / 503 / 504 / 500 by kind; the BODY the page
  reads is unchanged; a refused entry stays 200.
- **L5** `constructor` / `__proto__` as an action name caused a false "fault" for the Admin. Now "Unknown action".
- **L6** The every-minute version check also ran in background tabs. Now only when the page is looked at.
- **L7** Security headers: `Content-Security-Policy` (objects, base, forms, framing) enforced; the script rule is sent as
  report-only (nothing can break; violations show in the browser console) – see D10.
- Three code comments that said the opposite of the code were corrected; the Admin's "backup hours" (read from names no
  backup ever wrote) fixed; `.gitignore` covers `.env.*`.

## C. Checked and found in order (no change)

No secret or key in the repository (pattern scan; keys are read from the server's settings only) · the browser never talks
to Supabase and holds no database key · row level security on every table, no policy for the public roles, every
`security definer` function closed to them · only 5 entry points can be called, everything else through the action table,
module and Admin checks made on the server (`audit.js`: a no-access user is refused by every module action, a view-only
user by every edit action) · session token 44 random characters, ends on password change / deactivation / sign-out ·
sign-in: 5 wrong tries then locked, counted exactly, one message for every failure · passwords never sent to the page,
never in the Activity Log, hidden in the backup · the save lock is a real lock across servers; numbers (DI-, IN-, bill
no.) are taken under it · no "clear all" path; deletes go by id list · a formula can never be written into the backup
Sheet · the page escapes what it draws (1,816 insertions looked at; the ones found are in H1) · AI answers are escaped,
the AI gets look-up results and a 7,000-character snapshot, not the database; no bank / PAN / password data goes to it;
look-ups run with the asker's own rights · no `eval` in the app · the service worker never touches `/api/`.
